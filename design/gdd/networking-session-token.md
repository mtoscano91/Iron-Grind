# Networking — Session Token Spec

> **Status**: Approved (Pass 1 lean, 2026-05-14)
> **Author**: Manuel Toscano + agents
> **Last Updated**: 2026-05-14
> **Parent**: networking-session.md

## Overview

The session token is a 16-byte cryptographically random opaque identifier generated by the server on session establishment. Its sole purpose is to let a reconnecting client prove it owns the session without re-running full authentication. The token is stored server-side, bound to a specific AccountID, rotated on every successful reconnect, and deleted on session expiry or invalidation. It is never persisted client-side to disk.

## Player Fantasy

Players never see tokens. This spec exists so that "the server knows it's still me" — a reconnecting client on a flaky 4G connection is recognized and resumes within seconds. Token failure is invisible too: if the token mismatches, the player falls through to full re-authentication rather than a permanent error. The token is infrastructure that makes the CR-NET-6 reconnect contract feel seamless.

## Detailed Rules

**CR-TOK-1 — Token Generation**
On every `Connecting → Connected` transition, the server generates a new token using `RandomNumberGenerator.GetBytes(16)` (`System.Security.Cryptography`). Tokens are never reused across sessions for the same account.

**CR-TOK-2 — Token Delivery**
The server includes the 16-byte token as a fixed-length field in `SessionHandshake`. The client stores it in memory for the session. The client MUST NOT persist the token to disk — it is session-scoped and expires with the session.

**CR-TOK-3 — Token Presentation on Reconnect**
When reconnecting (entering `Reconnecting` state), the client includes its stored token in `ConnectionRequest` as a 16-byte field. A fresh connection with no prior session sends a zero-filled 16-byte field — the server recognizes this as a fresh-connect signal, skips token lookup, and proceeds with full auth.

**CR-TOK-4 — Token Validation**
On receiving a `ConnectionRequest` with a non-zero token field:
1. Server derives `AccountID` by normalizing `username` from `ConnectionRequest` and looking up the account record (same DB call as the credential path). If found, performs `ActiveSessionTokens[AccountID]` lookup. `AccountID` is never transmitted by the client — it is always derived server-side from the `username` field (per `auth-wire-messages.md`).
2. If no entry exists (session expired or never established): auth failure → `Disconnected_SessionExpired`
3. If entry exists but token does not byte-match: auth failure → same response
4. If entry exists and token matches: reconnect proceeds to `Reconnecting`

Comparison MUST use `CryptographicOperations.FixedTimeEquals` to prevent timing oracle attacks.

**CR-TOK-5 — Token Rotation**
After every successful `Reconnecting → Connected` transition:
1. Server generates a new 16-byte token
2. Stored at `ActiveSessionTokens[AccountID]` — overwrites old immediately
3. Delivered in the reconnect `ConnectionAccepted` message (S→C auth success message — see `auth-wire-messages.md`)
4. Old token is invalid from this point — any in-flight reconnect using the old token fails

**CR-TOK-6 — Token Invalidation Conditions**
Token is deleted from `ActiveSessionTokens` when:
- Session TTL elapses (`Disconnected_SessionActive → Disconnected_SessionExpired`)
- Explicit disconnect (`Connected → Disconnected_SessionExpired`, graceful logout)
- Session-stealing — prior token deleted before the new connection receives its token (B-NP-7)
- Server restart — in-memory store cleared (see EC-TOK-4)

**CR-TOK-7 — Token Binding**
Each `ActiveSessionTokens` entry is keyed by `AccountID` and contains `token: byte[16]`, `sessionId: Guid`, `expiresAtTick: uint`. `sessionId` is a per-session unique identifier used for server-side audit logging and session-event correlation — it allows server logs to reference a specific session instance rather than relying on `AccountID` alone, which is reused across sessions. A token from account A cannot authenticate account B. Cross-account lookup is structurally impossible.

**CR-TOK-8 — Server-Side Storage**
`ActiveSessionTokens` is an in-process dictionary on the game server. It is NOT persisted to disk or a distributed cache. The token is an ephemeral artifact. All tokens are cleared on server restart — see EC-TOK-4.

Access to `ActiveSessionTokens` must be thread-safe. Reconnect handlers and TTL expiry processing may execute concurrently at the 20 Hz tick boundary. Use `ConcurrentDictionary<uint, ActiveTokenEntry>` or a lock-guarded `Dictionary` — a plain `Dictionary` is not safe under concurrent access and will produce non-deterministic failures under load.

## Formulas

**F-TOK-1 — Token Entropy**

```
entropy_bits = TOKEN_LENGTH_BYTES × 8 = 16 × 8 = 128 bits
brute_force_at_50pct_preimage_pessimistic = 2^(128/2) = 2^64 ≈ 1.8 × 10^19
```

Birthday bound applied as pessimistic estimate (accounts for an attacker who can succeed by colliding with *any* of N active sessions rather than one specific token). Single-token preimage requires 2^128 average attempts — meaningfully higher. At a sustained attack rate of 10,000 reconnect attempts/second (far above `REAUTH_FAILURE_LIMIT` enforcement), the pessimistic bound requires ~1.8 × 10^15 seconds. Adequate for `SESSION_TTL_SECONDS` max = 600s.

**F-TOK-2 — Token Store Memory Overhead Per Session**

| Field | Size |
|-------|------|
| `token: byte[16]` | 16 bytes |
| `sessionId: Guid` | 16 bytes |
| `expiresAtTick: uint` | 4 bytes |
| Dictionary key + bucket overhead | ~24 bytes |
| **Total per session** | **~60 bytes** |

At 50 sessions per zone: `60 × 50 = 3 KB`. Negligible.

## Edge Cases

**EC-TOK-1 — Token for Expired Session**
Session has transitioned to `Disconnected_SessionExpired` (TTL elapsed); `ActiveSessionTokens[AccountID]` has been deleted. Server returns auth failure — identical response to a token mismatch. Client falls through to fresh connect flow.

**EC-TOK-2 — Token Mismatch (Wrong Value)**
Covers: corrupted client memory, stale token from a prior rotation, brute-force attempt. Constant-time comparison returns auth failure with no timing leak. Response is identical to EC-TOK-1 — no information about why the token failed.

**EC-TOK-3 — Zero Token (Fresh Connect)**
Client sends zero-filled 16-byte token field in `ConnectionRequest`. Server detects this as a fresh-connect signal, skips token lookup entirely, and proceeds with full authentication. Normal path for first-time connections and for clients that lost stored state.

**EC-TOK-4 — Server Restart (Token Store Cleared)**
On restart, `ActiveSessionTokens` is empty. Reconnecting clients receive auth failure and fall through to full authentication. If session data is valid in persistence (character state written before crash), the server re-establishes the session after successful auth and issues a new token. Session TTL tracking for persistence writes uses wall-clock anchoring; tick-based comparisons apply for in-session logic (see CR-NET-6.5 and OQ-NET-1).

**EC-TOK-5 — Concurrent Reconnect Attempts**
Two TCP connections from the same client (e.g., app crash during reconnect): the first `ConnectionRequest` to reach the server wins the token lookup. After token rotation on success, the second attempt receives auth failure.

**EC-TOK-6 — Session-Stealing with Valid Token**
A second device connects for the same account (session-stealing per B-NP-7 in networking-session.md). Server deletes `ActiveSessionTokens[AccountID]` before processing the new connection. Any subsequent reconnect with the original token receives auth failure. The new connection receives token T' in its `SessionHandshake`.

**EC-TOK-7 — Token Rotated but Handshake Delivery Failed**
If the connection drops after the server writes the new token to `ActiveSessionTokens` but before the client receives the reconnect `SessionHandshake`, the client retains its old (now-invalidated) token. Subsequent reconnect attempts with the old token receive auth failure identical to EC-TOK-2. After `REAUTH_FAILURE_LIMIT` consecutive failures, the session expires and transitions to `Disconnected_SessionExpired`; the client falls through to full authentication. No special server handling is required — the existing reconnect failure path covers this. This scenario is more likely on 4G mobile where mid-handshake drops are not rare.

## Tuning Knobs

| Knob | Default | Safe Range | Gameplay Impact |
|------|---------|------------|-----------------|
| `SESSION_TOKEN_LENGTH_BYTES` | 16 | [16, 32] | Token entropy per F-TOK-1. Must not decrease below 16. Increasing to 32 provides 256-bit entropy at +16 bytes per handshake — unnecessary for session lifetimes up to 600s. |

Token rotation policy (rotate on every successful reconnect) is a fixed security invariant, not a tuning knob.

## Acceptance Criteria

**AC-TOK-1** — Given a `Connecting → Connected` transition, `SessionHandshake` contains a non-zero 16-byte token field. The server has an `ActiveSessionTokens[AccountID]` entry with the same value.

**AC-TOK-2** — Given a player in `Disconnected_SessionActive` who sends a `ConnectionRequest` with the correct 16-byte token, the server proceeds to `Reconnecting` state. No second authentication challenge is issued.

**AC-TOK-3** — Given a `ConnectionRequest` with one byte of the token modified, the server returns auth failure. The session remains in `Disconnected_SessionActive`; the TTL continues.

**AC-TOK-4** — Given a successful `Reconnecting → Connected`, when the client subsequently sends a `ConnectionRequest` with the pre-reconnect token, the server returns auth failure and does not advance to `Reconnecting` state. Token rotation is confirmed by the old token's invalidation — if the old token fails, a new token must have been issued and stored. (Direct byte-comparison of old vs. new token values requires a `byte[] sessionToken` parameter in `OnSessionHandshakeEmitted`; deferred to when the full `SessionHandshake` schema is finalized per OQ-NC-SER-2.)

**AC-TOK-5** — Given a server restart with empty `ActiveSessionTokens`, a client whose session data is in persistence connects within its TTL window, completes full auth, and receives a new token in `SessionHandshake`. Character state is preserved (no rollback from the restart).

**AC-TOK-6** — Given two concurrent `ConnectionRequest` messages from the same client, only the first succeeds. After token rotation, the second returns auth failure.

**AC-TOK-7** — Given session-stealing (new device connects for same account), the original token is invalidated before the new connection's `SessionHandshake` is sent. The original token returns auth failure from that point.

**AC-TOK-8** — Given 1,000 `ConnectionRequest` messages with random tokens targeting a valid session, `REAUTH_FAILURE_LIMIT` triggers before any succeed; no timing difference is observable between match and mismatch comparisons (constant-time verified by benchmark, p < 0.05).
