## Overview

The session token is a 16-byte cryptographically random opaque identifier generated by the server on session establishment. Its sole purpose is to let a reconnecting client prove it owns the session without re-running full authentication. The token is stored server-side, bound to a specific AccountID, rotated on every successful reconnect, and deleted on session expiry or invalidation. It is never persisted client-side to disk.

## Player Fantasy

Players never see tokens. This spec exists so that "the server knows it's still me" — a reconnecting client on a flaky 4G connection is recognized and resumes within seconds. Token failure is invisible too: if the token mismatches, the player falls through to full re-authentication rather than a permanent error. The token is infrastructure that makes the CR-NET-6 reconnect contract feel seamless.

## Detailed Rules

**CR-TOK-1 — Token Generation**
On every fresh login the gateway generates a new token using `RandomNumberGenerator.GetBytes(16)` (`System.Security.Cryptography`) and hands it to the target zone in `Admit` (ADR-016; `authentication.md` CR-AUTH-11). On rotation (CR-TOK-5) the zone generates the new token the same way. Tokens are never reused across sessions for the same account.

**CR-TOK-2 — Token Delivery**
The gateway returns the 16-byte token as a fixed-length field in `LoginResponse` (`auth-wire-messages.md`); the client presents it to the zone in its `SessionHandshake`. The client stores it in memory for the session. The client MUST NOT persist the token to disk — it is session-scoped and expires with the session.

**CR-TOK-3 — Token Presentation on Reconnect**
To reconnect, the client sends its stored token in the 16-byte `tokenField` of `ConnectionRequest` to the gateway (`POST /v1/login`, `auth-wire-messages.md`). This is an HTTPS request, before any zone connection, so no zone session state changes on sending it. A client with no prior session sends a zero-filled field — the gateway treats it as a fresh login, skips token lookup and runs full authentication (EC-TOK-3).

**CR-TOK-4 — Token Validation (gateway `Reconnect`)**
On receiving a `ConnectionRequest` with a non-zero token field (ADR-016 Decision 4):
1. The gateway normalizes `username`, looks up the account record (same DB call as the credential path) and takes `AccountID` from it. It does not hash. If the account is unknown, banned (`is_banned`), or no zone holds a session for it, it returns `InvalidCredentials`. Otherwise it sends `Reconnect { accountId, token }` to the zone holding the session. `AccountID` is never transmitted by the client (`auth-wire-messages.md`, `authentication.md` CR-AUTH-2).
2. The zone looks up `ActiveSessionTokens[AccountID]`. No entry (session expired or never established): `ReconnectResult.accepted = false`.
3. Entry exists but the token does not byte-match: `accepted = false`. The failure is a failed re-auth attempt per `networking-session.md` ST-NET-1 / EC-NET-7 and counts toward `REAUTH_FAILURE_LIMIT`: below the limit the session ends in `Disconnected_SessionActive` with its TTL unchanged; at the limit it ends in `Disconnected_SessionExpired`.
4. Entry exists and the token matches: the zone rotates it in the same operation (CR-TOK-5) and replies `accepted = true` with the new token.

Steps 2–4 are one atomic `TryValidateAndRotate` call. Comparison MUST use `CryptographicOperations.FixedTimeEquals` to prevent timing oracle attacks. The client sees the same `InvalidCredentials` response for every failure in steps 1–3 — no information about why the token failed. (Anyone who knows a username can spend the `REAUTH_FAILURE_LIMIT` count and expire a live session — an accepted tradeoff, limited by private usernames: `authentication.md`.)

**CR-TOK-5 — Token Rotation**
On every accepted `Reconnect` (CR-TOK-4 step 4), atomically with validation:
1. The zone generates a new 16-byte token (CR-TOK-1)
2. Stored at `ActiveSessionTokens[AccountID]` — overwrites the old one immediately
3. Returned to the gateway in `ReconnectResult` and relayed to the client in `LoginResponse` (`auth-wire-messages.md`)
4. The old token is invalid from this point — any in-flight reconnect or handshake using it fails

Rotation happens before the client reaches the zone, so the client's `SessionHandshake` presents the rotated token (CR-TOK-9). The session stays in `Disconnected_SessionActive`, TTL running, until that handshake arrives.

**CR-TOK-6 — Token Invalidation Conditions**
Token is deleted from `ActiveSessionTokens` when:
- Session TTL elapses (`Disconnected_SessionActive → Disconnected_SessionExpired`)
- Explicit disconnect (`Connected → Disconnected_SessionExpired`, graceful logout)
- Session-stealing — prior token deleted before the new connection receives its token (B-NP-7)
- Entering-slot reclamation (`Connected → Disconnected_SessionExpired`, no persistence write) — `zone-instancing.md` CR-ZI-17: stall timeout or transport drop before `ZoneEntryAck` — the entry is deleted only if its `sessionId` (CR-TOK-7) is the reclaimed session's. A duplicate handshake (CR-ZI-17 case (b)) deletes nothing here: the new connection already logged in, so session stealing (row above) removed the old token and the entry holds the new connection's. No ghost exists, so the client's retry is a fresh connect (EC-TOK-1). *(Added 2026-10-23; sessionId guard and case (b) exclusion added in the zone-instancing lean verify the same day.)*
- Server restart — in-memory store cleared (see EC-TOK-4)

**CR-TOK-7 — Token Binding**
Each `ActiveSessionTokens` entry is keyed by `AccountID` and contains `token: byte[16]`, `sessionId: Guid`, `expiresAtTick: uint`. `sessionId` is a per-session unique identifier used for server-side audit logging and session-event correlation — it allows server logs to reference a specific session instance rather than relying on `AccountID` alone, which is reused across sessions. A token from account A cannot authenticate account B. Cross-account lookup is structurally impossible.

**CR-TOK-8 — Server-Side Storage**
`ActiveSessionTokens` (`SessionTokenStore`) is an in-process dictionary in the **zone server that holds the session**. The gateway fills it with `Admit` before the client is told where to go, and keeps no copy of the token after replying (ADR-016 Decision 4). It is NOT persisted to disk or a distributed cache. The token is an ephemeral artifact. All of a zone's tokens are cleared when that zone process restarts — see EC-TOK-4.

Access to `ActiveSessionTokens` must be thread-safe. `Admit` / `Evict` / `Reconnect` arrive on the gateway link thread (ADR-016) while handshake validation and TTL expiry run on the main thread. Use `ConcurrentDictionary<uint, ActiveTokenEntry>` or a lock-guarded `Dictionary` — a plain `Dictionary` is not safe under concurrent access and will produce non-deterministic failures under load. `TryValidateAndRotate` must stay a single atomic operation (CR-TOK-4).

**CR-TOK-9 — Zone Entry Token Check (`SessionHandshake`)**
Every zone entry — fresh login and token path alike — presents a token in `SessionHandshake(zoneId, characterId, token)`; this is the token validation of `zone-instancing.md` CR-ZI-8 step 3. The zone resolves `AccountID` from `characterId` through its own record — the admitted entry (`Admit`, fresh login) or the ghost session (token path) — then compares the presented token with `ActiveSessionTokens[AccountID]` using `CryptographicOperations.FixedTimeEquals`. The client never sends `AccountID`.
- **Match, fresh login:** entry proceeds (CR-ZI-8 step 3 onward); ST-NET-1 `Connecting → Connected` per `authentication.md` CR-AUTH-11. If the zone left Active after the `Admit` (it keeps the entry's token until `CONNECTING_TIMEOUT_SECONDS`), the reply is `ZoneFullResponse(ZoneDoesNotExist)` instead, with no `LoadCharacter` (`zone-instancing.md` CR-ZI-8 step 3, EC-ZI-1; 2026-11-06).
- **Match, token path:** ST-NET-1 `Disconnected_SessionActive → Reconnecting` ("session token matches"), then the CR-NET-6.4 sequence and `Reconnecting → Connected`. The token is not rotated again here.
- **No record for `characterId`, or mismatch:** the connection is closed with no message. No session changes state, the TTL keeps running, and the attempt does **not** count toward `REAUTH_FAILURE_LIMIT` (user decision 2026-11-06 — counting would let anyone who learns a `CharacterID` and zone port expire a ghost; guessing 128 bits per handshake is infeasible, F-TOK-1). Logged once per connection.

A client that receives `LoginResponse` but never arrives leaves the session in `Disconnected_SessionActive`; the TTL expires it (fresh login: the `CONNECTING_TIMEOUT_SECONDS` admitted-entry clock, ADR-016).

## Formulas

**F-TOK-1 — Token Entropy**

```
entropy_bits = TOKEN_LENGTH_BYTES × 8 = 16 × 8 = 128 bits
brute_force_at_50pct_preimage_pessimistic = 2^(128/2) = 2^64 ≈ 1.8 × 10^19
```

Birthday bound applied as pessimistic estimate (accounts for an attacker who can succeed by colliding with *any* of N active sessions rather than one specific token). Single-token preimage requires 2^128 average attempts — meaningfully higher. At a sustained attack rate of 10,000 reconnect attempts/second (far above `REAUTH_FAILURE_LIMIT` enforcement), the pessimistic bound requires ~1.8 × 10^15 seconds. Adequate for `SESSION_TTL_SECONDS` max = 600s.

**F-TOK-2 — Token Store Memory Overhead Per Session**

| Field | Size |
|-------|------|
| `token: byte[16]` | 16 bytes |
| `sessionId: Guid` | 16 bytes |
| `expiresAtTick: uint` | 4 bytes |
| Dictionary key + bucket overhead | ~24 bytes |
| **Total per session** | **~60 bytes** |

At 50 sessions per zone: `60 × 50 = 3 KB`. Negligible.

## Edge Cases

**EC-TOK-1 — Token for Expired Session**
Session has transitioned to `Disconnected_SessionExpired` (TTL elapsed); `ActiveSessionTokens[AccountID]` has been deleted. Server returns auth failure — identical response to a token mismatch. Client falls through to fresh connect flow.

**EC-TOK-2 — Token Mismatch (Wrong Value)**
Covers: corrupted client memory, stale token from a prior rotation, brute-force attempt. Constant-time comparison returns auth failure with no timing leak. Response is identical to EC-TOK-1 — no information about why the token failed.

**EC-TOK-3 — Zero Token (Fresh Connect)**
Client sends zero-filled 16-byte token field in `ConnectionRequest`. Server detects this as a fresh-connect signal, skips token lookup entirely, and proceeds with full authentication. Normal path for first-time connections and for clients that lost stored state.

**EC-TOK-4 — Server Restart (Token Store Cleared)**
On zone restart, that zone's `ActiveSessionTokens` is empty and the gateway has no session for its accounts (the zone re-registers with an empty `liveAccounts`). Reconnecting clients receive auth failure and fall through to full authentication. A gateway restart clears no tokens: zones re-register with their live accounts. If session data is valid in persistence (character state written before crash), the server re-establishes the session after successful auth and issues a new token. Session TTL tracking for persistence writes uses wall-clock anchoring; tick-based comparisons apply for in-session logic (see CR-NET-6.5 and OQ-NET-1).

**EC-TOK-5 — Concurrent Reconnect Attempts**
Two token-path `ConnectionRequest`s for the same session (e.g., app crash during reconnect, a client retry after `LOGIN_HTTP_TIMEOUT_SECONDS`): both become `Reconnect`s to the same zone, and the atomic `TryValidateAndRotate` (CR-TOK-4) lets exactly one succeed. The other sees the already-rotated token, fails (counted toward `REAUTH_FAILURE_LIMIT`), and its client receives `InvalidCredentials`.

**EC-TOK-6 — Session-Stealing with Valid Token**
A second device connects for the same account (session-stealing per B-NP-7 in networking-session.md). The gateway sends `Evict` to the zone holding the session, which deletes `ActiveSessionTokens[AccountID]` before the gateway admits the new login. Any subsequent reconnect with the original token receives auth failure. The new login receives token T' in its `LoginResponse`.

**EC-TOK-7 — Token Rotated but Handshake Delivery Failed**
If the client's request fails after the zone rotates the token (CR-TOK-5) but before the client receives the `LoginResponse` carrying it, the client retains its old (now-invalidated) token. Subsequent reconnect attempts with the old token receive auth failure identical to EC-TOK-2, each counted per CR-TOK-4 step 3. After `REAUTH_FAILURE_LIMIT` consecutive failures, the session expires and transitions to `Disconnected_SessionExpired`; the client falls through to full authentication. No special server handling is required — the existing reconnect failure path covers this. This scenario is more likely on 4G mobile where mid-handshake drops are not rare.

## Tuning Knobs

| Knob | Default | Safe Range | Gameplay Impact |
|------|---------|------------|-----------------|
| `SESSION_TOKEN_LENGTH_BYTES` | 16 | [16, 32] | Token entropy per F-TOK-1. Must not decrease below 16. Increasing to 32 provides 256-bit entropy at +16 bytes per handshake — unnecessary for session lifetimes up to 600s. |

Token rotation policy (rotate on every successful reconnect) is a fixed security invariant, not a tuning knob.

## Acceptance Criteria

**AC-TOK-1** — Given a successful fresh login, `LoginResponse` contains a non-zero 16-byte token field, and the routed zone has an `ActiveSessionTokens[AccountID]` entry with the same value before the response is sent.

**AC-TOK-2** — Given a player in `Disconnected_SessionActive` whose client sends a `ConnectionRequest` with the correct 16-byte token, the zone replies `ReconnectResult.accepted = true` with a new token, the session stays in `Disconnected_SessionActive`, and no password is checked. When the client then sends `SessionHandshake` with the new token, the session transitions `Disconnected_SessionActive → Reconnecting`. No second authentication challenge is issued.

**AC-TOK-3** — Given a `ConnectionRequest` with one byte of the token modified, the gateway returns `InvalidCredentials`, the failure count increases by 1, the session remains in `Disconnected_SessionActive` (below `REAUTH_FAILURE_LIMIT`) and `sessionExpiryTick` is unchanged.

**AC-TOK-4** — Given an accepted `Reconnect`, when a `ConnectionRequest` with the pre-reconnect token is then sent, the gateway returns `InvalidCredentials` and the session does not advance to `Reconnecting`. Token rotation is confirmed by the old token's invalidation — if the old token fails, a new token must have been issued and stored. (Direct byte-comparison of old vs. new token values requires a `byte[] sessionToken` parameter in `OnSessionHandshakeEmitted`; deferred to when the full `SessionHandshake` schema is finalized per OQ-NC-SER-2.)

**AC-TOK-5** — Given a server restart with empty `ActiveSessionTokens`, a client whose session data is in persistence connects within its TTL window, completes full auth, and receives a new token in `LoginResponse`. Character state is preserved (no rollback from the restart).

**AC-TOK-6** — Given two concurrent `Reconnect`s with the same valid token for one session, exactly one returns `accepted = true`; the other returns `accepted = false`, and `ActiveSessionTokens[AccountID]` holds the token returned by the accepted one.

**AC-TOK-9** — Given a session in `Disconnected_SessionActive` after an accepted `Reconnect`, when a `SessionHandshake` for its `CharacterID` arrives with (a) the pre-rotation token or (b) one byte of the rotated token modified, then the connection is closed with no message, the session stays in `Disconnected_SessionActive`, `sessionExpiryTick` is unchanged and the `REAUTH_FAILURE_LIMIT` count is unchanged; a following `SessionHandshake` with the rotated token transitions the session to `Reconnecting`. A `SessionHandshake` for a `CharacterID` the zone has no record of is closed the same way.

**AC-TOK-7** — Given session-stealing (new device connects for same account), the original token is invalidated (by `Evict`) before the new login's `LoginResponse` is sent. The original token returns auth failure from that point.

**AC-TOK-8** — Given 1,000 `ConnectionRequest` messages with random tokens targeting a valid session, `REAUTH_FAILURE_LIMIT` triggers before any succeed; no timing difference is observable between match and mismatch comparisons (constant-time verified by benchmark, p < 0.05).
